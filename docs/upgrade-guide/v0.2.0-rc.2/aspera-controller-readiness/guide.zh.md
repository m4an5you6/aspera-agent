# Aspera 控制进程就绪检查

[English](guide.md) | 中文

## 变更

准备流程比较实际 GPU UUID、字符设备与控制进程启动时的授权。控制接口健康不代表环境兼容。所选准备 Agent 接收具体差异，可以调用 `repair_preparation_controller`；交接前仍须通过程序复验。新节点控制进程在分配实验时再次核对 GPU 身份。

经过认证的健康响应声明 `controller-readiness-v1` 和 `controller-maintenance-v1` 能力。维护操作原子拒绝被占用的控制进程，并在按身份停止进程前阻止新任务接入。`controllerRepairMaxAttempts` 默认为每个实验、服务器、角色两次。独立版本 1 修复回执保留上限、次数及结果未决状态；重复或恢复操作不重置次数。本地 fleet 存储仍为第 6 代，提交仍为协议 4，Session 格式不变。

本机密码 SSH 传输在认证前发生临时故障时，可在一次操作的截止时间内重连。派发提供[握手限制](../../../../extensions/aspera/packages/dispatch/README.zh.md#use-this-package)；已有准备使用当前本机限制，保留其原安装和发布记录。认证、主机密钥及认证后操作失败均不触发重复执行。连接检查的截止时间仍为 20 秒。

准备验收使用执行沙箱的命名空间及完整隔离。容器若允许基础 bubblewrap 探测，但在 `--unshare-user` 后拒绝挂载 `/proc`，则在交接前失败。原准备 Session 接收实际命令输出及所需平台操作；修复账号环境后仍须程序复验。隔离与设备授权保持生效。

## 迁移

1. 同步更新应用资源、生成类型和自定义 `FleetDriver` 消费者；提供方实现 `inspectController`。现有应用执行文件可以使用对应的资源更新。
2. 保留各实验的原发布和提交。旧控制进程可以通过限定、无凭据的进程设置只读探测。复用要求已记录启动 GPU 身份、当前设备匹配且使用原发布。旧进程需要重启但缺少安全维护能力时，必须确认任务已释放并由操作者停止；准备流程不替换其封存发布。
3. 重试前核对中断的修复。确认停止的回执或身份匹配的新进程允许恢复；缺少退出证据时阻止再次停止或启动。修复次数跨重试保留。
4. 已提交实验的 GPU 身份或设备要求变化时，复制为新实验。其固定计划和提交不被改写，执行不会自动重跑。见[控制进程就绪与恢复](../../../../extensions/aspera/docs/state-and-api.zh.md#controller-readiness)。
5. 通过兼容账号配置或云平台解除命名空间及 `/proc` 权限拒绝，再重试准备。保留所需隔离参数。已提交实验保持原发布；确认资源释放后，复制实验以使用更新后的执行资源。
