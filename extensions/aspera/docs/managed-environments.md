# Managed training environments

English | [中文](managed-environments.zh.md)

## Summary

Each experiment node registers an independent Python interpreter, dependency metadata and verified package references. Packages with matching artifact digest, source/build identity, Python ABI and wheel platform tags share immutable payloads on the selected data disk. Existing environments, releases, models, datasets and results remain retained.

[Server storage and fixed materials](storage-governance.md) defines account-side inventory, released legacy-environment borrowing, per-volume capacity reservations, historical duplicate cleanup and pinned model/data acquisition. These tools share the existing preparation and execution Agents; programs perform every acceptance check.

## Create and verify

The preparation Agent installs Python and the exact uv version from `asperaEnvironmentTools.uvVersion` in the fixed release manifest. Program inspection saves their actual executable paths. The execution Agent calls `inspect_experiment_environment` on an assigned node and requests `prepare_experiment_environment` with an environment name, UUID operation ID and `create`, `install`, `verify` or `make-writable`. `training` is the default environment; additional environments require a purpose and their own relative directory. Requests cannot change server ownership, device grants, the package store or process IDs.

`create` installs the supplied requirements, merging them with an existing environment's direct requirements. Compatible installed versions are reverified in place; conflicting constraints fail before publication and preserve the old generation. `install` explicitly replaces direct requirements through a private generation. Original requests and effective requirements are recorded separately. Empty requirements create only a verified base interpreter. uv resolves hash-pinned dependencies with builds confined to private sandbox directories and shared materials mounted read-only. Installation names the absolute interpreter and disables user-site loading; an invalid prefix fails instead of falling back to `.local`.

Every install checks the current environment, shared packages, verified materials and historical wheels before acquiring missing dependencies. A compatible unchanged environment is reverified without creating another venv. Locked resolutions retain requirement, interpreter, platform and uv identities across failed operations. Each operation publishes a dated reuse plan with decisions, download bytes, reused payload bytes, predicted peak space and measured added space. Peak estimates include already acquired private tools/materials plus remaining expansion and file metadata; the free-space check reserves only the remaining need and safety margin. Linked packages are excluded from full-payload installation budgets.

Program verification checks payload hashes, the actual interpreter prefix, disabled user-site loading, requested imports and `uv pip check`. Requested CUDA verification uses the installed torch interpreter. A torch package on a node granted NVIDIA GPU devices requires CUDA verification even if the request omits it. A failed import, dependency check or required CUDA check cannot publish a ready environment.

`prepare_experiment_environment` remains an exclusive pending tool until the node confirms the final receipt, process-group exit and admission release. Authenticated `environment-status` reads one experiment and operation without scanning packages. The original deadline survives reconnects and repeated calls; a lost submission reply triggers reads, never another submission. Defaults are `operationPollIntervalMs: 1000`, `timeoutMs: 1800000`, `readTimeoutMs: 30000`, `stopTimeoutMs: 30000` and `operationReconnectTimeoutMs: 60000`. Timeout requests node-owned termination; cancellation propagates to waiting and network requests. Unconfirmed exit or exhausted connection recovery returns an unresolved outcome and retains protection. `inspect_experiment_environment` accepts optional `operation_id` for this lightweight read.

The program generates and executes uv commands. A private installer contains the exact `asperaEnvironmentTools.pipVersion`; its standard wheel, tag and requirement parsers match the training interpreter's Python version and ABI. Training environments have no seeded distributions: pip, setuptools, packaging and wheel enter training only when requested or required by dependencies. Downloading and building use read-only installer contents; small installer files have independent copies rather than writable build-cache aliases. Program Python calls use isolated module lookup, including import verification. Dependency installation targets training. Tooling temporaries contribute to the space budget and `installerTemporaryBytes`. Verification of unchanged requirements retains the ready environment.

Wheel materials retain their original filenames. The installer's standard wheel/tag parser validates name, version, build and complete tags. Verified legacy materials whose filenames lost tags receive private installation aliases selected from declared tags in target preference order. The resolver, full-wheel installer and metadata-only shared installer use those aliases; original bytes and indexes remain unchanged. Hashes bind materials to locked sources; incompatible or damaged materials remain rejected.

Completion rechecks actual package contents against the last verified digests. A detached file changed by an ordinary command requires another `verify` operation before completion; a retained ready manifest cannot substitute for that check.

<a id="reuse-and-changes"></a>
## Reuse and changes

The server-owned store is `<namespaceRoot>/packages-v1`. Publication verifies wheel RECORD digests and the actual installed files before creating package references. Same-filesystem hard links are preferred. A failed hard link attempts the filesystem clone ioctl and verifies its content; unsupported cloning falls back to an independent copy only after a space-budget check. Each manifest records methods, reasons, predicted ordinary-copy bytes and measured added space. File identities deduplicate allocated-byte counts; clone savings remain explicitly estimated.

Verified wheels enter the content-addressed `materials` catalog before environment verification. Complete materials survive unrelated download or import failures. Shared packages use reduced wheels containing metadata and declared scripts: fixed uv creates private metadata and entry points, then the program links verified payload files and updates RECORD. Packages requiring other wheel data sections use the measured full-install path. Mutable historical wheels require one budgeted independent import; owned completed downloads are promoted without another compressed copy. Matching materials remain available to later operations and experiments.

Ordinary commands and inference services mount registered environments read-only. No permission change is applied to shared hard-linked files. Creating or deleting an environment link preserves other environments' paths and bytes. Upgrade builds a private generation and replaces only the current environment after its commands and services have exited; failed verification restores the retained generation. `make-writable` copies and atomically replaces only registered requested payload files. Subsequent verification updates modified content digests; modified files do not become unmodified shared package material.

Read-only legacy discovery lists installed metadata and cached wheels in server-owned experiment directories. Inspection reads candidate metadata; acquisition verifies complete RECORD data and searches wheels separately so installed metadata cannot consume the candidate budget first. The resolver first tries the verified local wheel catalog without an index; only an unsatisfied local resolution permits online resolution. Mutable installations remain unchanged and cannot become shared payloads directly. A wheel must match the resolved digest and target tags before import; private source builds additionally bind compiler, platform and GPU configuration. Only top-level wheel metadata identifies its distribution; legitimate nested vendor metadata is retained. Unknown, incomplete or corrupt sources retain a diagnostic; `legacyEntryLimit` defaults to 100000 visited entries and bounded scans report partial results.

<a id="space-and-cleanup"></a>
## Space and cleanup

`experimentStorageUsage(id)` returns node measurements and the original check time. The Host saves an independent version-1 copy under `$DSH_HOME/aspera-environments/<experimentId>/storage.v1.json`. Authenticated control reads take priority; a stopped controller permits read-only SSH inspection of the original saved placement. Failed reads retain the dated local copy and connection error. The overview distinguishes remote measurement, SSH reading and an offline copy.

References remain while remote environments exist, including after experiment completion or local-only record deletion. Confirmed remote experiment deletion releases its references only after the owned run and cleanup directory have disappeared. Shared packages become candidates only with no registered reference and no external hard link. Missing referenced files require reconciliation rather than automatic release.

Successful installation removes private download/build files through ownership checks; private uv caches use `uv cache clean`. Verified materials remain available for reuse. Storage-governance releases retain unique verified wheels and preview unreferenced managed objects, confirmed exited private files and verified duplicates with a retained copy. Historical candidates require explicit selection; pending references prevent collection. `cleanupExperimentCache(request)` binds nodes, preview fingerprints and operation IDs, refusing changed references or active commands/services. Owned recovery and cleanup can run below the execution reserve while retaining mount and ownership checks. Existing unregistered caches and old environments remain retained.

Cleanup opens directories and entries with `O_PATH` and `O_NOFOLLOW`, reads their current `mnt_id` from `/proc/self/fdinfo`, and deletes relative to retained directory descriptors. Different `st_dev` values on one overlay mount are permitted; actual mount crossings, same-filesystem bind mounts, replaced directories and unreadable identities block cleanup. Internal symbolic links are unlinked without visiting targets. Diagnostics retain path, check stage, mount IDs and device numbers; saved mount IDs do not authorize later operations.

Verification, reference persistence, generation publication and temporary cleanup have separate records. After successful publication, an ordinary unlink failure retains the verified environment and a version-1 pending cleanup record. Safety failures and uncertain process outcomes still block execution. Ordinary commands and services mask retained operation directories with read-only empty mounts, preventing private hard-link aliases from exposing shared packages. Package and material references remain until physical cleanup completes. The overview distinguishes a verified environment with pending cleanup from an unverified environment.

## Recovery and compatibility

Recovery rechecks publication, directory generation and private residue even when the original receipt already confirms exit. Independent version-1 recovery records preserve the original receipt and times. A published generation is retained for verification; interrupted replacement restores the prior generation when available. A failed stage without a usable generation remains evidence, allowing another preparation under the original environment identity. The Agent subsequently requests `prepare_experiment_environment` to verify the interpreter, user-site isolation, dependencies, imports and required CUDA; missing dependencies use the same environment identity. Repeated recovery reads its saved result; changed generation or receipt identity returns a conflict.

A selected fixed manifest with `asperaEnvironmentTools.cleanupVersion: 1` additionally requires `managed-environment-cleanup-v1` before controller reuse and handover. An old experiment keeps its original release and outcome; confirm resource release, then copy it to use a repaired release and verified reusable materials.

Manifest `asperaEnvironmentTools.installVersion: 3` requires `managed-environment-install-v3` for isolated fixed-pip tooling and package-conflict retry checks; version 2 remains readable with its own capability. Controller and worker launches omit pip settings for older fixed releases. A v3 controller cannot replace an older release's installer during reuse. Independent version-1 runtime records retain the original deadline, stop reason, observed exit and admission release; effective requirements preserve request identity. Runtime, launch, receipt and reuse records join the local archive and owned experiment cleanup. The overview distinguishes verified base interpreters, verified dependencies, active installation and exit verification using program-recorded times. Existing fixed releases require a new experiment after confirmed resource release.

Structured shared-file conflicts persist in `environment-operations-v1/<operationId>/failure.v1.json` and optional receipt `failure`. Checks bind the environment, normalized requirements, installer implementation, Python/tool versions, platform, sandbox, GPU configuration and retained generation. Identical inputs stop before installer/training creation or dependency resolution; changed requirements still stop before acquisition and installation when the same conflicting wheel identities remain selected. New operation IDs, create/install changes and unrelated dependencies cannot repair that conflict. Relevant input changes permit fresh verification while preserving the original failure and process-exit protection. Transient connection and unclassified failures retain their existing recovery behavior.

Environment manifests, package references and operation receipts use independent version-1 files. Requests are content-bound and idempotent. A server package lock serializes installation, publication and collection; a persistent admission marker blocks new experiment commands during mutation. References are flushed before ready-state publication. Disk or write failures preserve existing records. Unknown exits retain the marker until Linux process-group and host-boot evidence confirm the original operation ended; recovery restores the saved generation or requires fresh verification of a committed generation. Cleanup interruption retains its remaining candidates and requires a fresh preview rather than blindly repeating deletion.

`inspect_experiment_environment` is read-only; atomic plans remain readable during installation while cleanup eligibility is unconfirmed. `recover_experiment_environment` reconciles an original operation without a model-supplied PID or path. Separate startup journals distinguish prepared, starting, started, rejected and exited operations; pending reads retain original times. Rejection before spawn is recorded and reconciled. Legacy operations without command or startup evidence remain fenced for investigation. The execution Agent also receives `preview_experiment_cache_cleanup` and `cleanup_experiment_cache`; failures retain the original environment instead of creating another installation directory.

The Host flushes a cleanup receipt before sending a deletion request. Restart recovery reads only the original operation status, never resubmits deletion, and blocks remote experiment removal while an exit remains unconfirmed. Local-only removal stops Host reads and writes without releasing remote package references.

Capabilities `managed-environments-v1` and `managed-environment-reuse-v1` identify authenticated environment operations and pre-install reuse/recovery. A fixed manifest with `asperaEnvironmentTools.reuseVersion: 1` requires the latter before controller reuse and handover; an older healthy controller needs the existing controlled idle repair. Plans, material indexes, resolution records and startup journals are independent version-1 files. Submission protocol 4, fleet generation 6, Session events and original submissions remain unchanged. Old experiments retain their fixed release and environment. Requests, diagnostics and verification results use tool events in the original execution Session. Local removal waits for Host I/O; remote references remain until confirmed remote deletion.

The Linux filesystem tests and keyless worker/Web replays exercise their respective local mechanisms. True 4090-1 environment imports, file identity and disk increments require the server to be reachable. CUDA acceptance additionally requires an available GPU; unavailable checks remain recorded as pending.
