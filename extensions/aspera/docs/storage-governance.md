# Server storage and fixed materials

English | [中文](storage-governance.zh.md)

## Summary

Aspera's preparation and execution Agents request storage observations, environment reuse and fixed model/data materials through scoped tools. The Host resolves selected servers and original submissions; the node measures, verifies, reserves, installs and downloads. No additional orchestration Agent or Agent-loop modification is involved. Existing environments, models, datasets, results, logs and sealed releases remain retained.

<a id="account-inventory"></a>
## Account inventory

Preparation's `inspect_server_storage` uses the SSH login account. Execution's `inspect_experiment_storage` uses the same node service. Owned roots come from the saved placement, controller storage-root registry and ownership markers. Capacity observations also include configured local mount prefixes without adopting or recursively scanning unowned directories. Account writability, sandbox writability and hidden historical directories remain separate observations; an unknown value stays unknown.

Storage selection saves each assignment with its corresponding inventory in one local record update. Unsubmitted preparation retries reobserve the same selected directories, verify the original server, experiment, release and mount identities, then commit both records together. Changed free space can refresh the observations; changed ownership, mounts, unwritable storage or insufficient capacity block retry. Existing paths, releases, environments, models and logs remain fixed. Submitted experiments retain their original submission.

The catalog distinguishes releases, environments, installation packages, models, datasets, temporary files, checkpoints, results, logs and other owned files. Logical sizes count directory entries; physical allocation counts each device/inode once. Filesystem free space is measured independently. Unattributed usage includes unscanned and unowned data; it is not a cleanup authorization. A bounded scan saves its cursor and original measurement time. The overview reads the saved catalog; Refresh or Continue scan explicitly requests more work. Changed root ownership or volume identity prevents adoption.

`managedEnvironments.governance` configures `scanEntryLimit: 100000`, `scanTimeoutMs: 10000`, `snapshotFileLimit: 200000` and `verificationTimeoutMs: 300000`. Exceeded or unreadable scans remain incomplete. `inventoryMountPrefixes` controls capacity-only discovery. Mount IDs describe the current observation and never grant cross-restart authority.

<a id="storage-registration"></a>
## Storage registration

Copied containers retain historical disk observations. `verify_server_storage` in preparation and `verify_experiment_storage` in execution bind an `operationId` to the `rootId` and `observationId` returned by inspection. The program verifies ownership, actual mount, directory identity and writability under the shared admission lock. Live writers or unconfirmed prior process identities prevent registration; the requesting Agent may remain active on its unchanged fixed placement. Registration never kills a process, releases an allocation or moves an experiment directory. A changed fixed experiment placement remains blocked.

The journal is saved before registration. Identical retries recover the same operation; a changed observation requires a new inspection. The current pointer selects an immutable registration history entry while original root observations remain retained. New registrations invalidate prior candidate IDs, scan cursors, borrowed-environment proofs and material-file proofs. Canonical manifests retain their material identity; current content must verify again. Agent investigation order and candidate choice remain independent of registration.

Persistence acknowledgement: registration observations, requests, histories and pointers use independent `version: 1`, `formatVersion: "0.1.3"` records under `state/storage-governance-v1/registrations-0.1.3`. Borrowing and material evidence add optional `registrationId`; legacy records remain readable until a new registration requires fresh proof. New fixed releases declare `registrationFormat: "0.1.3"` and require `storage-registration-0.1.3`, `bounded-diagnostics-0.1.3` and `command-admission-0.1.3`. Their preparation registers selected roots through the same verifier. Older fixed releases do not receive this preparation action. Fleet generation 6, remote protocol 4, original submissions and material format 0.1.2 remain unchanged.

<a id="historical-environments"></a>
## Historical environments

`prepare_experiment_environment` checks an existing managed `training` environment first. Otherwise it verifies released historical candidates before creating another environment. Optional `reuseCandidateId` selects a program-issued candidate. The source allocation, terminal resource release, command/service release, process state, interpreter, ABI, RECORD contents, links, `.pth` paths, dependencies, requested imports and required CUDA must verify. Fixed uv checks dependency constraints through a temporary read-only metadata mount; the training environment needs neither pip nor packaging for this check. Source files stay unchanged. Metadata directories alone do not establish a usable environment. Incomplete discovery blocks an automatic second installation.

`historical-environment-precheck-v1` rejects unsupported direct-source constraints before source verification. After source release is confirmed, a metadata-only check rejects missing unconditional pinned distributions before hashing package contents or executing the historical interpreter. Incomplete metadata, legacy layouts and additional `.pth` paths defer to full verification; conditional requirements remain with uv. Passing this preliminary check never publishes a binding or replaces integrity, dependency, import or CUDA verification.

A matching source is bound as a verified historical installation, not as a verified wheel origin. The program atomically retains a source lease before publishing the destination binding. Commands and inference services mount only the environment and required interpreter paths read-only, keep other source-experiment files hidden and use the returned absolute interpreter. User packages and bytecode writes are disabled. Source-file, interpreter-link or volume changes require reverification. Source commands, mutation and remote deletion are refused while a binding remains. Publication and source deletion share the controller admission lock. `make-writable` cannot change a borrowed source.

Borrowing performs no dependency installation or second venv creation. Unsatisfied candidates retain concrete differences. An explicit independent installation uses its own budget and existing managed-generation behavior; it never patches the source. Same-volume verified package stores can contribute linked wheels and package payloads without expansion. Cross-volume cache import is reported separately rather than silently copying all historical packages. Environment and source references survive completion and local-only record deletion; confirmed remote binding deletion releases the consumer reference.

<a id="capacity-and-cleanup"></a>
## Capacity and cleanup

Purpose placement groups capacity by actual filesystem device, so directories and bind mounts share one reserve. `managedEnvironments.governance` adds `systemReserveBytes: 5368709120`, `systemReserveRatio: 0.10`, `dataReserveBytes: 2147483648` and `dataReserveRatio: 0.05`; each disk retains the largest of its absolute, proportional and existing minimum-free margins. `peakSafetyFactor: 1.20` covers additional download, unpack/build, copy and coexistence estimates. `capacityRecheckMs: 5000` bounds lightweight checks during active managed installation without rescanning the catalog.

Optional `environmentEstimate: { peakBytes, basis }` declares a reasoned additional peak, not a verified installed size. `allowEnvironmentFallback: true` first checks historical reuse. If data storage still cannot fit, the program may register an unused training environment on the controller's system filesystem. Every remaining model/data/output volume must fit, and the system target must fit its peak, peer reservations and margin. Existing environment requests, installation receipts or published environments prevent relocation. Unknown estimates remain pending; insufficient targets retain per-volume deficits and the unsuccessful fallback assessment.

The separate environment workspace and package store do not change the submitted data workspace or material identities. Publication, read-only command mounts, historical reuse and confirmed remote deletion verify their ownership and filesystem. Applied fallback produces one official floating Toast with a storage-detail action; its management-profile claim survives navigation, reload and restart. Closing the notice retains placement history.

`assess_experiment_storage` binds a UUID operation, environment requirements, canonical material IDs, output bytes and checkpoint bytes. It calculates each mounted volume independently. Missing materials, remaining environment peak, required independent copies, output/checkpoint growth and the existing minimum-free reserve are checked together. Verified reuse does not count another full installation. Unknown dependency estimates remain pending. Already measured result/checkpoint growth reduces the remaining declared output reserve. A ready deployment reserve alone is not training-capacity acceptance.

Installation, material acquisition and ordinary commands with a declared capacity plan repeat program checks. Server-owned reservations coordinate other experiments; identical physical material content is not reserved twice. Reservations remain after connection loss or uncertain process exit. Confirmed node release removes capacity reservations; retained environment/material references have a separate lifetime. The ordinary shell interface is not a filesystem quota, and shell keyword matching is not used to infer resource needs.

Cleanup preview includes confirmed exited private installation residue, unreferenced managed package objects and duplicate verified wheels with a retained valid copy. Unique verified wheels, environments, model/data content, checkpoints, scripts, results, logs and releases are excluded. Historical candidates require selected candidate IDs and the original preview fingerprint. Cleanup rechecks references, process exit, source identity and store locks. Descriptor-relative deletion and actual mount IDs retain traversal, symbolic-link and nested/bind-mount protection. A partial cleanup keeps its receipt and remaining evidence; ordinary temporary unlink failure does not invalidate a verified environment. Safety or exit uncertainty remains blocking.

<a id="fixed-materials"></a>
## Fixed model and dataset materials

`inspect_experiment_materials` obtains a canonical Hugging Face repository and immutable 40-character revision manifest, including every selected file's size and SHA-256 or Git-blob identity. `files` selects required content. The Host can fetch the same bounded canonical metadata when the node cannot reach it, then submits it through an authenticated program endpoint. Mirror transport is checked against canonical bytes. ModelScope accepting a revision parameter does not attest a Hugging Face commit; a direct provider request without supported immutable attestation remains blocked.

`canonicalDatasetVersion: 1` requires `canonical-modelscope-dataset-v1`. For `provider: modelscope` datasets, the Host uses Git to verify the exact official commit, tree and ordinary blob or LFS identities without checkout or LFS payload acquisition. Git must be available on the Host; metadata output and temporary repository size use `managedEnvironments.readBytes`, with the existing read deadline, polling and cancellation. The canonical document retains `source: {provider: "modelscope", method: "git-commit-tree-v1"}`. The node independently checks the requested identity and file contents. Model mirrors continue to require the canonical Hugging Face manifest. Installation also rejects a partial budget that omits previously registered material IDs.

`prepare_experiment_materials` accepts an inspected material ID and original operation ID. Read-only `verify` needs no download budget and does not publish. `acquire` requires a ready capacity-plan ID; `recover` preserves the original action. Verified historical files may be referenced read-only after source-release checks without another weight copy. New downloads write beside their final data-volume location and publish after verification. Completed files and verified partial shards survive failure; ranged downloads validate offsets and complete content. Shared files use hard links first, tested copy-on-write next and fresh capacity admission before independent copying.

One owner downloads each material identity. Server transfer slots default to one; matching requests reuse durable state. Tools wait for the final receipt, actual exit and admission release. `materialTimeoutMs` defaults to 7200000, `metadataWaitTimeoutMs` to 120000 and `networkReadTimeoutMs` to 30000; polling and reconnection use the existing environment operation settings. Reconnection never resets the original deadline. Cancellation and timeout retain stop reasons and require exit confirmation before recovery. Model-visible diagnostics and results remain in the original Session.

`materialRecoveryVersion: 1` requires `managed-material-recovery-v1`. A completed verifier can still require exit settlement. If settlement fails, tools return the diagnostic and original operation identity without waiting for the download deadline. `recover` rechecks the original command's confirmed exit and other active work, then commits settlement without launching another verifier or download. Live or unconfirmed processes retain their admission restriction. Failed helper reads preserve both stdout and stderr.

Persistence acknowledgement: `material-operations-v1/<operationId>/settlement-failure.v1.json` is an independent version-1 diagnostic bound to its experiment, node and operation. Material responses add optional `settlementError`; consumers distinguish it from download failure. Successful recovery removes the resolved diagnostic only after settlement and admission release. Existing receipts, releases, protocol 4, fleet 6 and Sessions retain their formats.

Commands and inference services use the returned local paths through read-only mounts. Registered materials default Hugging Face, Transformers and Datasets to offline loading, avoiding a second framework-managed download. Material bindings and file stamps are rechecked at command launch and completion. Program-recorded hard-link creation permits its expected inode metadata change while unrecorded file changes fail validation.

<a id="targeted-material-verification"></a>
## Targeted material verification

The Agent chooses investigation order. Both storage inspection tools accept `scope_json`: `{kind:"account"}`, `{kind:"experiment",experimentId}`, or `{kind:"directory",rootId,relativePath}` under a confirmed root. Cursors bind node, scope and observed mount identity. `materialCandidates` identify owned directories, not verified payloads. Pass a candidate's `reuseCandidateId` to material inspection and verification without completing unrelated account scans. Hidden or unscanned content never establishes account-wide absence.

Canonical requests persist before network access. `metadataSource` selects `auto`, `node`, `host` or `cache`; auto uses trusted cached manifests, a node probe and the Host bridge. `metadataProbeTimeoutMs` defaults to 10000 and must be shorter than `managedEnvironments.readTimeoutMs`; payload download settings are unchanged. Pending requests retain one deadline across reconnects and restarts. Metadata access never hashes large payloads. Managed verification saves completed file digests with device/inode, size and time identities; changed files invalidate checkpoints. Source ownership, canonical hashes and release still must pass before reuse.

Capacity `coverage` separates `assessmentScope: "declared"` from `"experiment"`. Declared readiness covers only supplied needs. For experiment scope, register `materialRequirements: {planRevision,complete,materials:[{kind,repository,revision,files?,materialId?}]}`. Missing bindings, unresolved canonical metadata or unverified historical candidates remain pending. Requirements are Agent declarations checked against canonical records, not inferred from plan prose. Verified direct reuse contributes no duplicate weight allocation; independent copies retain their actual peak and reserves. Cleanup preview discovers recorded duplicate wheels without synchronous full hashing; the managed cleanup verifies both selected and retained copies before deletion.

Persistence acknowledgement: targeted candidates, operation associations, material requirement declarations and per-file checkpoints use independent `version: 1`, `formatVersion: "0.1.1"` records. Catalogs and capacity plans add optional scope, candidate and coverage fields; original readers remain available. Manifest `asperaEnvironmentTools.materialFormat: "0.1.1"` requires `targeted-materials-0.1.1`. Original remote releases receive only their supported policy fields and cannot silently accept new operations. Updating desktop resources does not resume blocked experiments or replace their sealed releases.

Material identity is independent of its directory. Inspection observes canonical content and default assets; an optional candidate describes that source without selecting it for subsequent operations. Verification accepts `materialId` and an explicit `reuseCandidateId` in either discovery order, binds the source before launch and retains per-file verified, missing, mismatch, unreadable and unverified results. Older releases verify default assets when the candidate is omitted; capable releases use the automatic selection below. Repeated equivalent requests identify the original operation; recovery retains its source, checkpoints and deadline.

Capacity selects verified sources with `materialSources: [{materialId,verificationOperationId,mode}]`, where `mode` is `readonly` or `copy`. Receipts must belong to the experiment, node and approved plan. Read-only reuse requires every canonical file. Copy can retain verified files and obtain missing or damaged files in a separate managed target; unknown files keep assessment pending. Hard-link or clone failure requires capacity for independent copying before bytes are written. Source files remain unchanged, and every required canonical file, including repository metadata, must pass before publication.

Source snapshots, operation file results, capacity estimates and experiment-specific publications use `version: 1`, `formatVersion: "0.1.2"`. Published bindings and sandbox mounts consume the corresponding experiment publication rather than a mutable global source. Compatibility leases retain source protection for older cleanup readers until confirmed consumer deletion. Manifest `materialFormat: "0.1.2"` requires `material-source-bindings-0.1.2`; original operations and legacy records retain their readers and cannot silently adopt a new source. These independent records leave fleet generation 6, protocol 4 and submitted digests unchanged.

<a id="automatic-history-reuse"></a>
## Automatic historical reuse

Owned ready-environment manifests seed discovery before cached legacy directories. They are hints, not verification receipts: source release, full contents, dependencies and required CUDA still verify. Within one verification, storage registration and mount observations are shared across files and rechecked before publication. Cleanup checks reuse only identity-matched reference metadata; a preview hashes each unchanged physical release asset once, while later previews obtain fresh content proofs.

Releases declaring `asperaEnvironmentTools.reuseVerificationVersion: 1` require `storage-reuse-verification-v1`. New verification without an explicit candidate discovers equivalent owned sources and selects minimum additional storage; explicit candidates retain their exact source. Current bindings precede managed and historical sources, with stable candidate ordering. A verified zero-addition source needs no unrelated full inventory. Cache links must remain inside an authorized repository cache and use a protected managed view when published. Original operation selection and deadlines remain fixed.

Discovery saves bounded directory cursors; registration changes require new discovery and verification. Scan pages default to 10000 ms and must be shorter than the 30000 ms read limit. Deep verification runs as a node-owned operation with the existing 300000 ms budget, lightweight status polling and retained per-file proofs. A read timeout does not stop that operation. Source-release protection precedes hashing; publication rechecks ownership and file identity. Read errors distinguish cancellation, timeout, output limits and process failure, preserving private diagnostics.

Capacity assessment consumes settled source receipts without starting scans or publishing environment loans. Omitted registered requirements and incomplete reuse remain pending. Verified sources remove duplicate payload allocation; missing files, copies, output and checkpoint reserves remain charged. New matching plans supersede old deficit evidence without deleting history. `inspect_experiment_environment` returns bounded summaries and accepts saved `details_json` pages; `storageToolResultBytes` defaults to 8192. Object pages include scalar `value` fields within that budget and retain each field's `page`; absent values require a detail read. Full observations retain their original check time and join the run archive.

Persistence acknowledgement: discovery, selection, verification progress, registered capacity requirements and tool observations use independent version-1 records. Discovery cursor frames add optional `registered` and `manifestOffset` for the bounded manifest pass; older frames remain readable. Material operations add optional `reuse`, `discovering` and verified cache mappings; environment plans add `checking-reuse`; capacity plans add optional reuse state. Existing records remain readable, and previous operations preserve their source semantics. Original releases, protocol 4, fleet generation 6 and Session format remain unchanged.

<a id="storage-preflight"></a>
## Environment preflight and retention policies

Releases declaring `storagePreflightVersion: 2` require `storage-preflight-v2`. `prepare_experiment_environment` action `verify-reuse` checks an existing source without installing or publishing. Its `preflight` distinguishes reusable, repair-required, incompatible and unknown sources. RECORD size mismatches are checked before full snapshot hashing. The Agent chooses borrowing, a program-issued repair plan or another candidate; old files remain unchanged.

`assess_experiment_storage` defaults to `mode: preview` on capable releases. Trials retain estimates without publishing the current admission plan or reserving bytes. IDs supplied in `materialRequirements` join `materialIds`; a complete requirement set defaults to experiment scope unless the caller explicitly chooses declared scope. `mode: commit` selects an approved policy revision and requires settled environment investigation. Correcting byte estimates keeps the same retention policy; explicit byte minima still apply. Source proofs bind the original plan, Session, release and current file identities. Unknown reuse cannot become a zero-byte estimate.

Releases declaring `requirementLedgerVersion: 1` require `storage-requirement-ledger-v1`. Dependency trials and failed commits cannot amend the published environment's requirements. Reassessment checks the current managed manifest or verified historical binding and lists omitted dependencies explicitly. Agents change the dependency set through the environment installation tool, then reassess; earlier trials remain readable. Registered fixed materials, approved retention minima and source verification remain required.

Approved plan `storagePolicy` describes artifact type, checkpoint count, optimizer/scheduler state, required recovery points, explicit byte minima and rationale. `get_experiment_storage_policy` reads current decisions. The Agent uses `propose_experiment_storage_policy` for semantic changes; Host approval or rejection compares the expected revision. Automatic mode accepts only proposals preserving all originally approved requirements. Manual confirmation waits inside the tool without model polling and never grants an Agent approval access. Policy reads use a separate lock from directory inventory. The overview shows pending differences and retains the original plan steps.

Material verification separately records `verificationStatus: complete|partial|none|unknown` and `materialReady`. A normal investigation can finish with partial content; acquire still needs an admitted budget and complete canonical publication. Matching files are retained while only missing bytes are obtained. Network reuse and cross-filesystem copy costs are reported separately. Partial investigations and preview deficits do not independently establish a whole-experiment failure.

Persistence acknowledgement: preflight, retention proposals/decisions and trial/admission associations use independent version-1 records. Existing operation readers retain their original interpretation; protocol 4, fleet 6, Sessions and submitted records stay fixed. New consumers also read optional preflight, budget mode/policy revision and material verification fields. Original experiments must release resources before copying to a capable release.

`reconsiderExperimentStoragePolicy(id, proposalId, expectedRevision)` lets an operator explicitly approve a successor to a rejected Agent proposal. Proposed contents are unchanged; the original rejection is retained and the successor records its proposal identity. Revision and node/plan checks still apply. Automatic mode waits for Host confirmation when a proposal reduces approved retention; it cannot approve the reduction itself.

<a id="agent-selected-environment-repair"></a>
## Agent-selected environment repair

Agents choose another historical candidate, request source rechecking, or select a program-issued `repairPlanId` with `prepare_experiment_environment(action: "repair")`. Repair preserves the effective requirements and environment identity; changing dependencies uses `install`. Proposals bind the experiment, node, original operation, requirements and source evidence. The program checks those identities and original process exit before installation. Download, copy and peak estimates remain unknown until material resolution and space checks finish.

Repair assembles a private generation from verified materials and publishes it after interpreter, dependency, import and required CUDA verification. Matching shared payloads retain their hard links; only missing materials are acquired. Historical environments and RECORD files remain unchanged. Unchanged content failures reuse source-specific proofs; `recheckSource: true` explicitly requests another check. Timeouts and unreadable sources are not cached as corrupt. Empty requirements create only a base interpreter unless an existing binding or explicit candidate selects historical borrowing.

`inspect_experiment_environment` decodes the node response before paging storage observations, operations, launches, diagnostics and repair plans. Failed scans retain their original error and process records; missing measurements remain unknown. Known legacy wrappers remain readable, with unconfirmed process state when independent exit evidence is absent.

Source-release checks distinguish the original task from current allocation commands that only read its retained files. Exemption requires verified owned ancestry, matching process/start/boot identities, an active command and disjoint writable roots; children may create private sessions. Installation, cleanup, unknown processes and conflicting ownership remain blocking. `readonlyConsumerVersion: 2` requires `readonly-source-consumers-v1` and `readonly-source-consumers-v2`. Acceptance failures keep a stable error description and expose each saved diagnostic location separately, so a fresh diagnostic ID cannot prevent finalization.

Cleanup preview exposes `referenceRepairs` separately from file candidates. Agents select eligible IDs through `reference_repair_ids`; Host requests use `referenceRepairIds`. Reference-only requests delete no cache files. Confirmation requires storage ownership, original deletion evidence, terminal task and process release, no retained borrowing and unchanged reference identity. A durable confirmation precedes release of the selected reference; original manifests, results and logs remain. Missing evidence keeps the reference protective while other inspection results remain available.

Training commands require complete capacity coverage when coverage is recorded. A declared-scope ready plan cannot establish whole-experiment readiness. Registered model/data requirements, environment allocation, output/checkpoint reserves and safety margins remain charged until verified reuse replaces their allocation.

Persistence acknowledgement: diagnostics and repair proposals use independent version-1 files in `environment-diagnostics-v1` and `environment-repair-plans-v1`; reference confirmations use `environment-reference-releases-v1`. Server-owned `environment-failures-v1` stores cached content failures with source identities and verification rules. `operation-contexts-0.1.1/environment-operation` binds completion evidence to its original plan and Session. Original receipts remain unchanged. New readers accept existing records. The repair action, optional receipt observations and reference selections require updated consumers. New writers require `asperaEnvironmentTools.repairVersion: 1` and `managed-environment-repair-v1`; older fixed releases receive neither repair nor reference-confirmation operations. Protocol 4, fleet generation 6 and Session format remain unchanged.

## Records and compatibility

Purpose placement persistence acknowledgement: `storage-arrangement.v1.json` uses `version: 1` and business `formatVersion: "0.1.0"`, binding node/experiment ownership, original and environment workspaces, filesystem evidence and a stable fallback event. Capacity plans add optional format, estimate basis, safety factor, actual capacity/device, new peak, deficit and fallback assessment; observations add optional `arrangement`. Legacy records without these fields remain readable; future business formats use `0.1.x`. Fleet generation 6, remote protocol 4 and original request digests remain unchanged.

Manifest `asperaEnvironmentTools.storageFormat: "0.1.0"` requires `purpose-storage-0.1.0`. Older fixed releases receive only supported policy fields. Storage-capability changes follow controlled idle repair; updating desktop resources does not restart remote experiments. Aspera remains 0.1.1 on DSH 0.2.0-rc.2.

Persistence acknowledgement: [storage schemas](../packages/experiments/src/storage-governance.ts) add independent version-1 catalog, historical environment snapshot/binding/lease, capacity plan/reservation, canonical material/index/reference and operation records. Controller-owned indexes live under `state/storage-governance-v1`; experiment-owned borrowing, plan, binding and operation files stay beside the original run. Material receipts preserve original request identity and deadline; runtime records retain observed stop and exit information. New operation records join the existing local archive. Original environment manifests, failed receipts and sealed releases remain unchanged.

Optional storage observations expose catalog, borrowing summaries, plans, materials and their operations. `experimentStoragePlan(id)` reads saved plans and `refreshExperimentStorage(id, serverId, cursor?)` explicitly advances account-side inventory. Existing storage and cleanup APIs retain their parameters; selected candidate IDs are optional extensions. Consumers update together. Offline views preserve measurement times and connection diagnostics; missing counts are not fabricated. Deletion awaits Host reads before removing local observations and rejects late replies.

Manifest `asperaEnvironmentTools.storageVersion: 1` requires `storage-governance-v1`, `historical-environment-borrow-v1` and `managed-materials-v1` in preparation, controller reuse and handover. Existing protocol-4 experiments retain their fixed implementations. Confirm their resource release, then copy an experiment to use these tools; original hardware requirements, outcomes and directories are not rewritten. Protocol 4, fleet generation 6 and Session format remain unchanged. Connection checks remain read-only, model-free and limited to 20 seconds.

Run `pnpm -C extensions/aspera run test:storage:qwen -- <isolated-config.json>` on the authorized Linux node with a private test release, the selected model snapshot and its credential file. The runner uses production profiles and scoped tools, records actual model responses, processes operator policy decisions through authenticated APIs and verifies resource release. Keep these results separate from keyless replays, CUDA and formal training; synthetic success cannot replace actual server observations.
